# 작업 단위 진행

리드(사용자가 연 메인 세션)가 실행한다. 사람은 **범위 확인 한 번과 PR 머지 한 번**만 한다.

## 1. 준비

1. `git switch main && git pull`로 최신을 받는다. Docs는 세션 시작 훅이 최신으로 받았는지 확인한다 (`../Docs`가 main이고 최신인지).
2. `docs/PLAN.md`에서 단위 `<N>`의 범위와 기준을 읽는다. 앞 단위가 머지되지 않았으면 멈추고 묻는다.
3. 브랜치를 만든다: `git switch -c feat/<N>-<영문 이름>`.
4. 앞 단위의 진행 기록이 `docs/progress/`에 남아 있으면(그 단위 PR이 머지됐다는 뜻) `git mv`로 `docs/progress/archive/`에 옮기고 `docs/PLAN.md`의 그 단위 상태를 "완료"로 고친다. 옮기기 전에 그 기록의 "남은 일"에서 아직 안 끝난 것을 `docs/PLAN.md` 해당 단위의 "앞 단위에서 넘어온 일"로 옮기고, Docs에 올릴 후속은 PLAN.md 끝 "Docs 후속"에 모은다.

## 2. 범위 확정 (사람 확인)

1. `docs/progress/_TEMPLATE.md`를 복사해 `docs/progress/unit-<N>.md`를 만든다. 그 단위의 "앞 단위에서 넘어온 일"(`docs/PLAN.md`)도 범위 표에 넣는다.
2. Docs에서 이 단위에 해당하는 FR·AC, API 경로, R- 규칙, ERD 테이블을 모두 찾아 범위 표에 적는다. AC마다 테스트 이름을 미리 정한다.
3. **"읽을 곳" 표**를 채운다. 범위 표를 만들며 찾은 위치를 그대로 적는다: 묶음마다 문서와 행 범위(또는 절 제목: PRD FR, API.md 경로·R- 규칙, ERD 테이블), 고칠 기존 코드 파일과 마이그레이션 번호. 구현 담당과 리뷰어는 이 표만 읽고 시작한다 (같은 탐색을 되풀이하지 않게).
4. 문서끼리 다르거나 비어 있는 곳이 있으면 여기서 멈추고 사용자에게 묻는다 (Docs 수정은 Docs 레포의 `/prd-sync`로).
5. 사용자에게 범위 표를 보여 주고 "맞으면 **start**"라고 묻는다. 승인 전에는 코드를 쓰지 않는다.

## 3. 구현

1. `server-implementer` 서브에이전트에게 진행 기록 경로를 주고 구현을 맡긴다. 범위가 크면 도메인별로 나눠 순서대로 맡긴다 (같은 파일을 동시에 고치지 않게). 작은 단위는 나누지 않는다.
2. **구현 담당은 단위마다 한 명을 이어 쓴다** (토큰 절약).
   - 첫 단계만 새로 부르고, 다음 단계와 리뷰 수정은 `SendMessage`로 같은 에이전트에게 보낸다. 이미 읽은 문서·코드를 다시 읽지 않는다.
   - 이어 쓰기는 **세 번까지**. 그 뒤, 또는 `SendMessage`가 없는 환경(옛 Claude Code)이면 새로 부르고 진행 기록의 "다음 단계용 메모"부터 읽게 한다.
   - 단계가 끝날 때마다 구현 담당이 "다음 단계용 메모"(만든 파일, 핵심 클래스, 주의점, 몇 줄)를 남긴다.
   - 이어 쓴 단계의 서브에이전트 토큰이 새로 부른 단계보다 많아지면(캐시가 안 맞는 경우) 그 단위는 새로 부르는 쪽으로 바꾼다.
3. 지시문에는 진행 기록 경로, 이번 묶음, "읽을 곳 표의 이 묶음 행만 읽고 그 밖은 필요할 때 grep"을 적는다. CLAUDE.md는 에이전트가 자동으로 받으니 읽으라고 하지 않는다.
4. 끝나면 `./gradlew build`(Docker 없으면 컴파일만)를 직접 돌려 확인한다. Gradle이 안 도는 환경(클라우드 세션)이면 첫 커밋 때 draft PR을 열고 CI로 확인한다.

## 4. 리뷰 반복

1. 리뷰 범위는 단위의 위험도로 정한다.

   | 경우 | 리뷰 |
   | --- | --- |
   | 권한(R- 규칙)·보안·동시성·데이터 삭제가 걸린 단위 (인증, 공간 접근, 스케줄러, 정리 작업, 파일 저장 등) | `server-reviewer` 1회. 리드가 opus로 지정할 수 있다 (예: 단위 6 알림 스케줄러). Critical이면 재리뷰 |
   | 보통 기능 단위 | `server-reviewer`(sonnet) 1회 |
   | 리뷰 수정분, 작은 fix·chore (파일 몇 개) | 리뷰어 없이 리드가 diff로 확인 |

2. 리뷰어는 매번 새로 부른다 (구현 과정을 모르는 눈으로 보게). 지시문에는 단위 번호, `git diff origin/main...HEAD`, 읽을 곳 표, "특히 볼 곳"을 준다. CI가 확인한 것(컴파일, 테스트 통과)은 다시 보지 않게 하고, Docs는 읽을 곳 표의 행만 대조하게 한다.
3. Critical·Major는 구현 담당(이어 쓰는 그 에이전트)에게 고치게 한다. Major 수정분은 리드가 diff로 확인하고, Critical이 있었으면 고친 뒤 다시 리뷰한다. 결과를 진행 기록의 "리뷰 기록"에 남긴다.
4. Critical이 3번 리뷰를 거쳐도 남으면 멈추고, 남은 문제를 PR 본문 맨 위 "⚠️ 사람 확인 필요"에 적는다.

## 5. PR

1. `docs/PLAN.md`의 상태를 "PR 완료"로, 진행 기록 상태를 바꾼다.
2. 커밋: `feat(<도메인>): <단위 이름> (<대표 FR>)`. push 후 `gh pr create --base main`.
3. PR 본문: 요약, 다룬 FR·AC·R ID와 테스트 이름 표, 리뷰 결과, 문서와 다르게 한 점(없어야 정상), 새 환경변수(있으면 `docs/SETUP.md` 반영 여부), 남은 일.
4. `gh pr checks --watch`로 CI를 기다린다. 실패하면 고쳐서 다시 push 한다.
5. **머지하지 않는다.** 사용자에게 PR 링크와 결과를 짧게 알린다.
